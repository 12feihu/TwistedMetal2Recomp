# The password system

Recovered from the encoder at **`func_8012CDFC`** and the validator at
**`func_8012CE7C`**, and verified against every published password on the
community cheat list — all decode, checksums included.
`tools/tm2_password.py` implements it both ways.

## Format

Six symbols, read left to right as a base-5 number:

| Symbol | Value |
|---|---|
| `_` blank | 0 |
| `△` triangle | 1 |
| `○` circle | 2 |
| `✕` cross | 3 |
| `□` square | 4 |

That 14-bit value is laid out as:

| Bits | Meaning |
|---|---|
| `0` | always 0 — the encoder clears it, the validator rejects it if set |
| `1-3` | level − 1 (valid levels 2–8) |
| `4-8` | character + 4 — the **encoder** writes five bits here, the **validator** reads four |
| `9` | final-battle flag; if set, the level must be 8 |
| `10-13` | checksum = `((character + 1) × (level − 1)) mod 13` |

Character indices are the roster order from `docs/CARS.md`. Level 1 (Los
Angeles) has no password because the game starts there.

Both routines compute the checksum with a magic-multiply divide by 13
(`0x4EC4EC4F`), which is what fixes the modulus at 13.

## There are eight stages, not seven

Bit 9 is easy to mistake for a redundant "the level is 8" marker. It is not.
In the encoder it is the **third argument**, handed in by the caller:

```
8012CE2C  sll  $a2, $a2, 9      ; final flag — an argument
8012CE34  sll  $a1, $a1, 4      ; (character + 4) << 4
8012CE3C  sll  $a0, $a0, 1      ; (level - 1) << 1
8012CE64  sll  $v0, $v0, 10     ; checksum
8012CE68  addu $v0, $v0, $a2    ; ... summed, not or'd
8012CE78  andi $v0, $v0, -2     ; bit 0 forced clear
```

and the validator peels it back off as a separate **output byte**, alongside
the level and the character:

```
8012CEDC  srl $v0, $v1, 9 ; andi 1 ; sb 0($a3)   ; final flag  -> caller
8012CEE8  srl $v0, $v1, 8 ; andi 1 ; sb 0($a1)   ; spare flag  -> caller
8012CF10  sltiu $v0, $v0, 8                      ; if final, level must be 8
```

So level 8 has **two** passwords, differing by exactly 512:

| Level field | Bit 9 | Where it puts you |
|---|---|---|
| 8 | clear | Hong Kong |
| 8 | **set** | **Dark Tooth's final battle** |

Both carry the same checksum, because the checksum is computed from the level
alone. Eight entry points, not seven.

### About bit 8

The other flag the validator returns is bit 8 — and the encoder never sets it.
`character + 4` reaches at most 15 for the twelve selectable characters, and
the final flag lands in bit 9, so **no password the stock game produces has
bit 8 set**. It is a dead output. That is what makes it safe to reclaim, which
is exactly what the fix below does.

## Why Dark Tooth's password can never be entered

Playing as Dark Tooth, the game displays a password on the pause screen — a
different one for every level. It is **not a placeholder**, and it is not
random. It is a genuine password produced by the same generator. It simply
cannot be typed back in.

**The generator and the validator disagree about the size of one field.**

The generator writes `character + 4` as a **five**-bit value spanning bits
4–8. The validator reads only **four** bits (4–7), and treats bit 8 as a
separate flag.

For characters 0–11 this never matters: `character + 4` is 4–15, fits in four
bits, bit 8 stays clear, and the password round-trips.

For the three characters that are not normally selectable it breaks:

| Character | Index | `char + 4` | Nibble the validator reads | Decodes to |
|---|---|---|---|---|
| Sweet Tooth | 12 | 16 | 0 | −4 → rejected |
| Minion | 13 | 17 | 1 | −3 → rejected |
| **Dark Tooth** | **14** | **18** | **2** | **−2 → rejected** |

The validator's `sltiu ..., 12` then throws it out. The overflow also lands in
bit 8, which is a second, independent rejection.

The checksum, meanwhile, is computed from the **real** index — so the password
looks entirely legitimate. That is why it appears on every level and why it
looks like it ought to work.

This is also exactly why the published tables list passwords for twelve
characters and state that Sweet Tooth and Minion have none. It is not that
nobody wrote them down; the format cannot express them.

### Worked example

A pause screen while playing as Dark Tooth in Paris shows:

```
△ ○ _ _ ○ ✕
```

Which is `1,2,0,0,2,3` base 5 = **4388**:

```
bit 0            0                    ok
bits 1-3    =    2   -> level 3       Paris                    correct
bits 4-7    =    2   -> char -2       REJECTED (needs 0..11)
bit 8       =    1   -> overflow of char+4 = 18
bits 10-13  =    4   -> checksum, and ((14+1)*(3-1)) mod 13 = 4   correct
```

Level and checksum are right. Only the character field is unrepresentable.

## Every Dark Tooth password the game will show

Generated by the same rules, so these should match what appears on the pause
screen. All are rejected by the unmodified game, and all are accepted with
`tm2.password-fix` enabled (below).

| Stage | Password |
|---|---|
| Moscow | `_ ✕ ✕ ✕ ○ ✕` |
| Paris | `△ ○ _ _ ○ ✕` |
| Amazonia | `○ _ △ ○ ○ ✕` |
| New York | `○ ✕ ○ □ ○ ✕` |
| Antarctica | `✕ △ □ △ ○ ✕` |
| Holland | `□ _ _ ✕ ○ ✕` |
| **Hong Kong** | `_ ○ _ ✕ _ △` |
| **Dark Tooth — final battle** | `_ ○ □ ✕ ○ ✕` |

The last two are the pair described above: the same stage, differing only in
bit 9, and they are **not** interchangeable. The final-battle code drops you
straight into the boss fight.

Note that six of the eight end `○ ✕`. That is a genuine arithmetic
coincidence, not a quirk of the character. For Dark Tooth the checksum is
`(15 × (level−1)) mod 13` = `2(level−1) mod 13`, and for levels 2–7 that is
exactly `2(level−1)` with no wrap. The value is then

```
v = 2(level−1)·1024  +  288  +  2(level−1)  =  2(level−1)·1025 + 288
```

and `1025 ≡ 0 (mod 25)`, so `v ≡ 288 ≡ 13 (mod 25)` — the last two symbols are
pinned to `○ ✕` regardless of the level. At Hong Kong `2×7 = 14` wraps to 1,
the identity breaks, and the tail moves. A near-constant tail is still a
decent tell that a password belongs to an unrepresentable character, but the
reason is this coincidence rather than anything structural.

## Generator

`tools/password_generator.html` is a self-contained page — pick a driver and a
stage, get the six symbols. Open it directly in a browser; there is no build
step and no network dependency beyond the webfonts.

It uses the same rules as the validator, so selecting Sweet Tooth, Minion or
Dark Tooth shows the code the game itself would display **and** explains why
that code is refused on entry.

## Command line

```bash
python tools/tm2_password.py decode "T O _ _ O X"
python tools/tm2_password.py encode --char 7 --level 2
python tools/tm2_password.py table  --char 14
```

Symbols are typed as `_ T O X S`.

## The fix — `tm2.password-fix`

Since the disagreement is entirely on the validator's side, it can be repaired
without touching the generator or changing a single published password. Three
instructions:

| Address | Stock | Patched | Why |
|---|---|---|---|
| `0x8012CEC0` | `andi $v0, $v0, 15` | `andi $v0, $v0, 31` | read the character field as five bits |
| `0x8012CED4` | `sltiu $v0, $v0, 12` | `sltiu $v0, $v0, 15` | accept characters 0–14 |
| `0x8012CEE8` | `srl $v0, $v1, 8` | `srl $v0, $v1, 14` | move the spare flag off bit 8 |

The third is required because bit 8 now belongs to the character field, so the
old "bit 8 must be clear" test would reject every high character on the very
next line. Bit 14 is safe to move it to: six base-5 symbols top out at 15624,
below 2^14, so bit 14 is clear for every representable password and the flag
reads zero exactly as it always did.

Nothing downstream re-checks the character. The caller at `0x8012F424` takes
the decoded outputs straight to the setters at `0x801377FC`, `0x80137814` and
`0x801378A4`.

**Verified exhaustively:** all 120 character/stage combinations (15 characters
× 8 entry points) round-trip under the patch, and none of the twelve
normally-valid characters changes behaviour. Dark Tooth in Paris —
`T O _ _ O X`, value 4388 — decodes to character 14, level 3. Confirmed in
game: the code is accepted and starts the run as Dark Tooth on the right
stage.

Ships as `mods/preloaded/packages/tm2.password-fix/`, **default disabled**,
with each patch guarded on the stock word so it fails closed on any other
revision.

### Discovery versus modification

Worth keeping the two apart. That the game *computes and displays* real
passwords for these three characters, on every level, with correct checksums,
is a **discovery** — it was always there. Making the validator accept them is
a **modification**. The mod does not unlock anything the game was hiding; it
resolves a contradiction between two halves of the game's own code.

The three patched words are also small enough to carry back to real hardware
as a code or a disc patch, which is the point.
