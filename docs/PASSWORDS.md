# The password system

Recovered from the validator at **`func_8012CE7C`** and verified against every
published password on the community cheat list — all decode, checksums
included. `tools/tm2_password.py` implements it both ways.

## Format

Six symbols, read left to right as a base-5 number:

| Symbol | Value |
|---|---|
| `_` blank | 0 |
| `△` triangle | 1 |
| `○` circle | 2 |
| `✕` cross | 3 |
| `□` square | 4 |

That 14-bit value is laid out as:

| Bits | Meaning |
|---|---|
| `0` | must be 0 |
| `1-3` | level − 1 (valid levels 2–8) |
| `4-7` | character + 4 (valid characters 0–11) |
| `8` | flag; must be clear unless bit 9 is set |
| `9` | final-stage flag; if set, level must be ≥ 8 |
| `10-13` | checksum = `((character + 1) × (level − 1)) mod 13` |

Character indices are the roster order from `docs/CARS.md`. Level 1 (Los
Angeles) has no password because the game starts there.

The validator computes the checksum with a magic-multiply divide by 13
(`0x4EC4EC4F`), which is what fixes the modulus at 13.

## Why Dark Tooth's password can never be entered

Playing as Dark Tooth, the game displays a password on the pause screen — a
different one for every level. It is **not a placeholder**, and it is not
random. It is a genuine password produced by the same generator. It simply
cannot be typed back in.

**The generator and the validator disagree about the size of one field.**

The generator writes `character + 4` as a **five**-bit value spanning bits
4–8. The validator reads only **four** bits (4–7), and treats bit 8 as a
separate flag.

For characters 0–11 this never matters: `character + 4` is 4–15, fits in four
bits, bit 8 stays clear, and the password round-trips.

For the three characters that are not normally selectable it breaks:

| Character | Index | `char + 4` | Nibble the validator reads | Decodes to |
|---|---|---|---|---|
| Sweet Tooth | 12 | 16 | 0 | −4 → rejected |
| Minion | 13 | 17 | 1 | −3 → rejected |
| **Dark Tooth** | **14** | **18** | **2** | **−2 → rejected** |

The validator's `sltiu ..., 12` then throws it out. The overflow also lands in
bit 8, which is a second, independent rejection.

The checksum, meanwhile, is computed from the **real** index — so the password
looks entirely legitimate. That is why it appears on every level and why it
looks like it ought to work.

This is also exactly why the published tables list passwords for twelve
characters and state that Sweet Tooth and Minion have none. It is not that
nobody wrote them down; the format cannot express them.

### Worked example

A pause screen while playing as Dark Tooth in Paris shows:

```
△ ○ _ _ ○ ✕
```

Which is `1,2,0,0,2,3` base 5 = **4388**:

```
bit 0            0                    ok
bits 1-3    =    2   -> level 3       Paris                    correct
bits 4-7    =    2   -> char -2       REJECTED (needs 0..11)
bit 8       =    1   -> overflow of char+4 = 18
bits 10-13  =    4   -> checksum, and ((14+1)*(3-1)) mod 13 = 4   correct
```

Level and checksum are right. Only the character field is unrepresentable.

## Every Dark Tooth password the game will show

Generated by the same rules, so these should match what appears on the pause
screen. All are rejected on entry.

| Level | Password |
|---|---|
| Moscow | `_ ✕ ✕ ✕ ○ ✕` |
| Paris | `△ ○ _ _ ○ ✕` |
| Amazonia | `○ _ △ ○ ○ ✕` |
| New York | `○ ✕ ○ □ ○ ✕` |
| Antarctica | `✕ △ □ △ ○ ✕` |
| Holland | `□ _ _ ✕ ○ ✕` |
| Hong Kong / Dark Tooth | `_ ○ □ ✕ ○ ✕` |

Note every one ends `○ ✕`. Bits 10–13 hold the checksum and bit 9 the
final-stage flag; with the character fixed at 14 the low symbols move only
with the level, so the tail is nearly constant. That repetition is a good
tell that a password belongs to an unrepresentable character.

## Usage

```bash
python tools/tm2_password.py decode "T O _ _ O X"
python tools/tm2_password.py encode --char 7 --level 2
python tools/tm2_password.py table  --char 14
```

Symbols are typed as `_ T O X S`.

## Could it be made to work?

The validator's character check is a single `sltiu` against 12 at
`0x8012CED4`, and the nibble read is the `andi ..., 15` just before it. Both
are in the EXE image, so both are reachable as guarded `main_exe` patches —
widening the field to five bits and the bound to 15 is a small change.

That would be a **mod**, not a discovery: it changes the game rather than
revealing something already present. Worth being clear about which is which.
